# OS Dungeon (OSダンジョン) 仕様書

サーバーのファイルシステムのディレクトリ階層を、Veloren本体のゲーム世界の中に**実際に歩ける3Dのボクセル空間**として生成する機能。既存のASCII版 `psy dungeon`(2D端末アプリ、[Setup.md](../Setup.md) 参照)を、実ゲーム内の3D空間に拡張したもの。

## 1. 目的

ディレクトリ階層を、ダンジョンの部屋・通路として直感的に見て回れるようにする。

- 対象: 開発者・デバッグ用途。一般プレイヤー向けの配布運用は想定していない(詳細は「7. セキュリティ上の位置づけ」)。
- 表示される部屋は「現在のディレクトリ」「親ディレクトリ」「兄弟ディレクトリ(現在地の前後2件まで)」「子ディレクトリ(先頭から最大5件まで)」の4種類。ツリー全体を一度に描画するのではなく、常に現在地を中心とした**ウィンドウ**だけを生成する。

## 2. 使い方

1. シングルプレイヤー/マルチプレイヤーでワールドに入り、チャット欄を開く(`Enter`)
2. `/osdungeon` と入力してEnter — 現在の(サーバープロセスの)作業ディレクトリを起点にダンジョンへ入室する
   - `/osdungeon <path>` のようにパスを指定すると、そのディレクトリを起点にできる(パスにスペースを含んでいても問題ない)
   - 入室すると、その場から真上に500ブロック浮遊した位置へテレポートし、無敵状態(`Invulnerability`バフ)になる
3. 部屋の中を歩いて配置を確認できる。各部屋の壁には、隣接するディレクトリの方向に向けて扉(穴)が開いている
4. もう一度 `/osdungeon` と入力すると退室し、入室前の位置へテレポートして戻る(無敵状態も解除)

デバッグ用に `/osdungeon_probe <dx> <dy> <dz>` コマンドもある。入室中のセッションの基準点(anchor)から見た相対座標の実際の地形ブロック種別を読み取り、チャットへの返信と `psypher/trace/dungeon_trace.jsonl`(下記参照)への記録の両方を行う。

## 3. アーキテクチャ

```
psypher-os-dungeon-game (独立クレート, psypher/os_dungeon/game/)
  └─ siblings_window() / children_window() / list_children()
       … Veloren非依存。std::fs のみに依存する純粋関数。
         隠しディレクトリ除外・ソート・読み取り不可ディレクトリのスキップ等を実装

veloren-server (server/)
  └─ /osdungeon, /osdungeon_probe チャットコマンド (server/src/cmd.rs)
       └─ os_dungeon::{enter, exit, navigate, probe} (実体は下記の通り物理的に移設済み)
            ├─ State::position_mut()        … テレポート(/goto と同じ、補正無しの単純代入)
            ├─ comp::Buffs (Invulnerability) … 滞在中の安全確保
            └─ draw_room() / punch_doorway() … State::set_block() でボクセルを直接書き込み

psypher-trace (独立クレート, psypher/trace/)
  └─ 生成した部屋・通路・ドアの座標や、/osdungeon_probe で実際に読み戻した地形を
     JSON Lines形式で psypher/trace/dungeon_trace.jsonl に記録する。
     スクリーンショットなしでも生成結果を検証できるようにするためのデバッグ基盤。
```

### ディレクトリ構成

```
psypher/
  os_dungeon/
    game/   … 共有ロジック(crate名: psypher-os-dungeon-game)。psy(ASCII版)と3D版の両方が利用
    cli/    … ASCII版 psy dungeon (crate名/コマンド名は psy のまま)
  server/
    src/os_dungeon/os_dungeon.rs
      … 3D生成ロジック本体。server クレートの一部としてコンパイルされる
        (`#[path]` 属性で参照。Server型・StateExtへの依存があるため、
         psypher-terminal のような完全な非依存クレート化はしていない)
  trace/  … デバッグ用トレーサー(psypher-os-dungeon 専用ではなく汎用)
```

### 部屋のレイアウト(上から見た図、縮尺は正確ではない)

```
                [兄弟 -2]
                [兄弟 -1]
[親, やや高い位置]   [現在の部屋]   [子0, やや低い位置]
                [兄弟 +1]              [子1, やや低い位置]
                [兄弟 +2]              [子2, やや低い位置]
```

親ディレクトリの部屋はやや高い位置、子ディレクトリの部屋はやや低い位置に配置している。ASCII版 `psy dungeon` の `<`(上昇)/`>`(下降)の階段記号を、3D空間での高さの違いとして表現したもので、実際のディレクトリの深さそのものとは無関係な演出。

各部屋は21×21×13ブロックの空洞の箱で、隣接する部屋の方向の壁に幅4×高さ6ブロックの扉(穴)が開いている。扉の真上には暗闇でも見えるよう発光ブロックの目印を置いている。

### 兄弟ディレクトリの接続

兄弟ディレクトリは現在の部屋と同じ通路軸(南北)に並ぶため、遠い兄弟(±2)を現在の部屋から直接つなぐと、間にある近い兄弟(±1)の部屋を素通りしてしまう。これを避けるため、兄弟は「現在の部屋 → 最も近い兄弟 → その次の兄弟」のように鎖状につないでいる(子ディレクトリは現在の部屋から見て東西方向に伸びる別軸に配置されるため、この問題は起きず、各子を独立して現在の部屋の壁につないでいる)。

## 4. 生成ロジックの詳細

生成ロジック本体は [`psypher/server/src/os_dungeon/os_dungeon.rs`](../../../server/src/os_dungeon/os_dungeon.rs) にある。

### 定数

| 定数 | 値 | 意味 |
|---|---|---|
| `ROOM_HALF` | `(10, 10, 6)` | 部屋の中心から壁までの距離。実際の部屋は21×21×13ブロックになる |
| `CORRIDOR_LEN` | `32` | 通路の水平距離(現状 `DRAW_CORRIDORS=false` のため未使用)。`LEVEL_SHIFT` に対して十分な余裕を持たせ、無理なく歩ける傾斜の階段になるようにする値 |
| `ROW_SPACING` | `30` | 兄弟・子の部屋を並べる間隔。隣接する部屋のシェルが重ならないよう `2 * ROOM_HALF.y` を超える値である必要がある |
| `LEVEL_SHIFT` | `16` | 親部屋を高く、子部屋を低く配置するオフセット |
| `ANCHOR_UP` | `500` | 入室時、現在地から真上に浮遊させる距離 |
| `WINDOW_RADIUS` | `2` | 兄弟・子ディレクトリを現在地の前後何件まで表示するか |
| `CORRIDOR_WIDTH` | `4` | 通路の幅(現状未使用) |
| `DOOR_Z` | `-5`(`-ROOM_HALF.z + 1`) | 扉の高さ方向の開始位置。部屋の床から1ブロック上 |
| `DOOR_HEIGHT` | `6` | 扉の高さ |
| `DRAW_CORRIDORS` | `false` | 通路生成の一時的なキルスイッチ(「6. 既知の制限」参照) |

### 部屋の描画(`draw_room`)

中心座標と半径を受け取り、その直方体の範囲を1回だけ走査し、境界面(シェル)は壁ブロック、内部は空気ブロックに設定する。「まず空洞の箱を作り、あとから壁に扉を開ける」という2段階構成になっている。

### 扉の穴あけ(`punch_doorway`)

通路本体(`carve_corridor`)とは独立した、1回で完結する単純な処理。壁の1面(`axis`: 0=X面・1=Y面、`sign`: どちら側か)に指定した幅・高さの穴を開け、その真上に発光ブロックを1つ置く。`along_offset` パラメータで、部屋の中心からずらした位置にも穴を開けられる — 例えば現在の部屋の東側の壁には、子ディレクトリの数だけ、それぞれ別の行(後述)に扉を開ける必要がある。複数ステップの補間を伴わないため、次項のバグの影響を受けない。

### 通路の彫り込み(`carve_corridor`、現状 `DRAW_CORRIDORS=false` により無効)

親・子ディレクトリの部屋は現在の部屋より高い/低い位置にあるため、通路は水平方向だけでなく垂直方向にも変化する「ランプ(緩斜面)」になる。開始点から終了点までを、水平・垂直の変化量のうち最大のものに合わせて等分割し、1ステップずつブロックを配置していく。

開発中に見つかったバグ: 隣接するステップの範囲が重なり合うため、後のステップの「床」の割り当てが、直前のステップで開けたばかりの「空気(通行可能な開口部)」を上書きしてしまうことがあった。特に出入り口の直後(最初のステップ)でこれが顕著に発生し、扉を開けたはずなのに実際の地形は塞がったままになる、という不具合につながった(`psypher-trace` + `/osdungeon_probe` で実際の地形ブロックを読み戻して確認・特定した)。

この修正として、各ステップの結果をその場で直接地形に書き込むのではなく、一旦ローカルなマップに蓄積してから最後にまとめて書き込む方式に変更した。「空気」の指定はどのステップの分であっても常に無条件で上書きし、「床・壁」の指定は「まだ何も割り当てられていない場合のみ」書き込む。これにより、各ステップがどんな順番で処理されても「空気が最終的に必ず勝つ」ことを保証している。

### 兄弟・子ディレクトリの配置

- **兄弟ディレクトリ(peer)**: `psypher-os-dungeon-game` の `siblings_window()` で、現在地の前後 `WINDOW_RADIUS`(=2)件を取得。現在の部屋を中心に南北方向へ `ROW_SPACING` 間隔で配置。前述の通り、遠い兄弟は近い兄弟を経由して鎖状に接続する
- **子ディレクトリ(child)**: `children_window()` で、先頭から `WINDOW_RADIUS * 2 + 1` 件(選択位置は常に0)を取得。現在の部屋を中心に東西方向へ配置。各子は自分専用の行(レーン)を通って独立に現在の部屋の壁とつながるため、兄弟のような鎖状接続は不要

### セッションとテレポートの順序

入室(`enter`)処理は次の順序で行う:

1. パスを解決する(引数が無ければサーバープロセスの作業ディレクトリ)
2. 現在位置を保存する(退室時に戻る場所)
3. アンカー座標(現在位置の真上 `ANCHOR_UP` ブロック)を計算する
4. **先に部屋・扉を描画してから、プレイヤーをテレポートさせる**
5. 無敵バフ(`Invulnerability`)を付与する
6. セッション情報(`OsDungeonSession`)を保存する

4の順序には理由がある。地形への書き込み(`State::set_block`)は即座に反映されるわけではなく、一旦キューに溜められてから適用される。そのため、テレポートを先に行うと、まだ描画が反映されていない(あるいは前回訪問時の残留物がある)場所にプレイヤーが送られてしまい、壁の中に埋まった状態になることがあった。

テレポート自体には、`/goto` と同じ「単純に座標を代入するだけ」の `position_mut()` を使っている。より高機能な `position_mut_reposition()`(近くの安全な場所へ自動で補正する機能)も試したが、この補正処理が上記の地形書き込みのタイミングと競合し、意図しない場所(レイアウト外の安全ネットの上など)に着地してしまう不具合につながったため、単純な代入方式に統一した。

### 安全ネット・クリア処理

- `clear_layout()`: 部屋・通路が取り得る最大範囲を、入室・移動のたびに一旦すべて空気に戻してから再描画する
- `draw_safety_net()`: レイアウト全体のさらに下に床を1枚敷いておく。通路が有効な場合に万一プレイヤーが部屋の外縁から落下しても、実際の地形(数百ブロック下)まで落ち続けることを防ぐための保険

### `TriggerZone`(将来の歩行検知用データ、現状は未消費)

`render_layout()` は各扉の位置・サイズと接続先ディレクトリのパスを `TriggerZone` の一覧として返す。現状はまだ何もこれを参照していない(「6. 既知の制限」参照)が、将来ECSのトリガー領域検知システムを実装する際に、この一覧をそのまま「プレイヤーがこの範囲に入ったら、このパスへ切り替える」という判定に使える形で、あらかじめ用意してある。

## 6. 既知の制限 (v1)

- **部屋同士をつなぐ通路(トンネル)は現状無効化されている**。各部屋の壁には隣接ディレクトリ方向への扉(穴)は開いているが、扉の外側は素通しの大気(何もない空間)で、部屋間を歩いてつなぐトンネル自体はまだ生成していない。ランプ状(高さが変わる)トンネルの床が出入り口を塞いでしまうバグを修正済みだが、そのうえで一旦トンネル生成自体をオフにして部屋のサイズ・扉の調整を優先した状態(`DRAW_CORRIDORS` 定数で切り替え可能)
- **通路を歩いての自動ディレクトリ移動はまだ未実装**。現状、ディレクトリを移動する唯一の方法は `/osdungeon <path>` を再実行すること(いったん退室してから、指定パスで入室し直す)。扉を歩いて通り抜けた瞬間に自動でcd相当の処理をする仕組み(ECSのトリガー領域検知システム)は未実装
- HUD上の「戻る」ボタンも未実装。退室は `/osdungeon` の再実行のみ
- `OsDungeonSessions` はサーバー側のみのリソースで、クライアントへレプリケートされていない。将来HUDボタンを実装する際は、クライアント側でローカルなフラグを持つ方式を想定(サーバーが黙って入室を拒否した場合にズレる可能性がある、という制約付き)
- `psypher-trace` は常時有効なデバッグ機構で、配布ビルドから除外するフィーチャーフラグ等は未整備

## 7. セキュリティ上の位置づけ

- `/osdungeon` および `/osdungeon_probe` はいずれも `Moderator` 権限を要求する。シングルプレイヤーでは自動的にAdmin権限が付与されるため、実質誰でも使える
- 生成処理は全てサーバー権威で行われる(クライアントからの自己申告位置やパスをそのまま信用しない)
- **この機能は「サーバープロセスから見えるファイルシステムのディレクトリ構造・名前」をそのままゲーム世界内に描画して見せる**という性質上、稼働中の実サーバーで一般プレイヤーに開放する運用は想定していない(Terminal機能と同様、開発者のローカル起動を前提とする)
- 生成される空間は元の地形から500ブロック上空に位置し、既存の地形やプレイヤーの建築物を一切上書きしない
